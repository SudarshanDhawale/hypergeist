# Manual verification: Ghost chat and AI settings

Spec: `.kiro/specs/ai-assistant-ui`. Do this list in a real browser before submission. The automated tests use scripted providers and a fake `fetch`, so they cannot show how a real model, a real provider, the deployed Worker, real zoom or real touch screens behave. This file covers the screen. The orchestrator itself (tool calls, JSON mode, limits, tokens) is in `docs/manual-verification-ai.md`, and the Worker routes are in `docs/manual-verification-worker.md`.

## How to use this file

**Never put a key in a file. Never paste a key into chat or into a screenshot.** Type a key only into the **Key** field of the AI settings window. The app keeps it in memory and asks for it again after a reload.

**Where the cases run.**

- **Local**: `pnpm --filter @hypergeist/web dev`, open `http://localhost:5173`. There is no Worker there, so demo mode falls back to the recorded examples. The counter stays hidden.
- **Deployed**: the Worker URL from `docs/deployment.md`, with the shared demo model on. Needed for the cases marked **Deployed Worker**.
- **Real provider**: a provider that allows browser requests and a key you own. Needed for the cases marked **Real provider**. Use at least two (for example Sarvam `https://api.sarvam.ai/v2` and OpenAI `https://api.openai.com/v1`), and one model on `http://localhost` if you have one. Write the provider and the model in the Result column, because results differ by model.

**The screen.**

- The menu bar has the title **HyperGeist**, the mode group **Mode** (**Interact**, **Edit**, **AI edit**), the button **Stacks**, the button **AI settings**, and the demo counter (when it shows).
- The **Ghost** window has the lines of the chat, the two example buttons **Make me a to-do list** and **Add a button**, the box labelled **Tell the Ghost what to do**, and the buttons **Send**, **Stop** (only while it works) and **Undo**. Under the sprite is the note: "Demo answers come from a shared model or recorded examples. The AI can make mistakes. Undo restores the stack as it was."
- The **AI settings** window has the choice **Demo (no key needed)** and **My own model**. With **My own model** it shows **Base URL**, **Model name**, **Key**, the button **Check this model**, and the buttons **Close** and **Save**.
- The **Stacks** window has the section **Make a stack with the Ghost** with the box **Describe the stack**, the button **Make it**, **Stop**, and the example buttons.

**Fresh window.** Where a case says "fresh window", use a new browser profile or a private window with no HyperGeist data.

**The recorded examples.** Only two sentences are recorded: `Make me a to-do list` and `Add a button`. A prompt must match after trimming, lower-casing, collapsing spaces and removing `.`, `!` and `?` at the end. Any other prompt in recorded mode gets the answer: `In demo mode I can only do these examples: "Add a button", "Make me a to-do list". Add your own key in Settings to try anything else.`

**The demo note.** When the shared model could not answer and the recorded examples did, the Ghost adds a note line: `The demo model could not be reached, so this answer is a recorded example.` When the shared model is busy it reads `The shared demo model is busy, so this answer is a recorded example.`

**How to read the cases.**

- Write **Pass**, **Fail** or a short note in the Result column. Name the browser and the provider if the result differs.
- The wording in "Expected" comes from the app's code. If the app shows different wording, write that in the Result column.
- A real model may do something a little different each time (different ids, labels, number of steps). That is fine if the stack stays valid and the request was understood. Write down what a bad answer looks like.
- Run the cases in order inside a group. Each group starts from a fresh window unless it says otherwise.
- The column "Needs" says **Local**, **Real provider** or **Deployed Worker**.
